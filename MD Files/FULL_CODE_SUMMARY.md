# TGMusicAI - Full Codebase File Summary

This document provides a comprehensive, human-readable summary of every file across all packages in the **TGMusicAI** application: `data/`, `utils/`, `playback/`, `cloud/` (`data/youtube/`), `alarm/`, and `ui/`. Each entry describes the file's purpose, design architecture, key functions, and a safety check for potential bugs or issues.

---

## 1. Data Layer (`data/`)

### 1.1 Entities (`data/local/entity/`)

#### `Song.kt` (`data/local/entity/Song.kt`)
* **Purpose:** Represents a musical track in the application database (local media or cloud streamable YouTube track).
* **Key Fields:**
  * `id`: Unique primary key auto-generated by Room (`Long`).
  * `title`, `artist`, `album`: Basic metadata strings.
  * `durationMs`: Track length in milliseconds.
  * `mediaUri`: Local file path, Content URI, or HTTP YouTube stream URL.
  * `producer`: Optional producer credits extracted by `AiMetadataCleaner`.
  * `lyrics`: Plain text or synced LRC string.
  * `artworkUri`: Local or remote album art image URI.
  * `youtubeId`: Optional YouTube video identifier used for deduplication.
  * `isDownloaded`: Boolean indicating if audio exists locally on device.
  * `isPinned`: Boolean flag for Speed Dial Home Tab pinning.
* **Bug / Health Check:** Clean Room `@Entity(tableName = "songs")` data class with safe defaults (`isDownloaded = true`, `isPinned = false`). No schema or type mismatch issues found.

#### `Playlist.kt` (`data/local/entity/Playlist.kt`)
* **Purpose:** Represents a user-created or system-generated (Smart) playlist.
* **Key Fields:**
  * `playlistId`: Unique primary key auto-generated by Room (`Long`).
  * `name`: Playlist title (e.g., "Liked Music", "Favorites").
  * `description`: Optional text description (added in Database Version 6).
  * `createdAt`: Epoch creation timestamp in milliseconds.
  * `isPinned`: Speed Dial Home Tab pin state.
  * `isSmart`: Flag designating auto-generated playlists (e.g. "Liked Music", "Top 50 Most Played", "Recently Added", "Unplayed").
* **Bug / Health Check:** Properly annotated for Room v6. Default values ensure safe instantiation. No issues found.

#### `PlaylistSongCrossRef.kt` (`data/local/entity/PlaylistSongCrossRef.kt`)
* **Purpose:** Junction entity defining the many-to-many mapping between `Playlist` and `Song`.
* **Key Fields:**
  * `playlistId` & `songId`: Compound primary keys referencing `playlists` and `songs`.
  * `position`: Ordering integer for custom song sequences in playlists.
* **Index:** Includes explicit index on `songId` to optimize reverse lookup queries (e.g. finding all playlists containing a specific song).
* **Bug / Health Check:** Correctly structured relational junction table. No issues found.

#### `SongStats.kt` (`data/local/entity/SongStats.kt`)
* **Purpose:** Stores playback telemetry and statistics separately from the primary `Song` entity to avoid database write contention during frequent playback updates.
* **Key Fields:**
  * `songId`: Primary key and foreign reference to `Song`.
  * `playCount`: Total play counter integer.
  * `lastPlayedAt`: Epoch timestamp in milliseconds of the last play event.
* **Bug / Health Check:** Lightweight and thread-safe design. No issues found.

#### `Alarm.kt` (`data/local/entity/Alarm.kt`)
* **Purpose:** Represents a user-configured musical alarm for full-screen lock-screen wake-ups.
* **Key Fields:**
  * `id`: Unique primary key (`Long`).
  * `timeInMillis`: Scheduled trigger timestamp or time of day in milliseconds.
  * `isEnabled`: Active status boolean.
  * `repeatDays`: Comma-separated day indicator string (e.g., "1,2,3,4,5").
  * `toneType`: Enum (`SONG`, `PLAYLIST`, or `RANDOM_LIKED`).
  * `toneUriOrId`: Song media URI or Playlist ID string.
  * `snoozeMinutes`: Snooze interval duration (default 10 mins).
  * `label`: Display label for alarm notification.
* **Bug / Health Check:** Clean Room entity data class. Enum `AlarmToneType` is properly handled. No issues found.

#### `PendingDownload.kt` (`data/local/entity/PendingDownload.kt`)
* **Purpose:** Tracks a YouTube download that's been queued/started but hasn't finished, so it can be resumed automatically if the app process is killed mid-download.
* **Key Fields:** `videoId` (primary key), `title`, `uploader`, `durationSeconds`, `queuedAt`.
* **Bug / Health Check:** Row is inserted on enqueue and deleted on any terminal state (completed or failed) by `CloudDownloadManager`. No issues found.

### 1.2 Data Access Objects (`data/local/dao/`)

  * `updateSongLyrics()`, `updateSongArtwork()`, `updatePinStatus()`, `updateDownloadStatus()`: Targeted field updates.
* **Bug / Health Check:** All SQL statements compile cleanly via Room KSP. Nullability and parameter binding are handled safely. No issues found.

#### `PlaylistDao.kt` (`data/local/dao/PlaylistDao.kt`)
* **Purpose:** Room DAO for managing playlists, smart playlists, cross-references, and safe cascading deletions.

  * `isSongInPlaylistFlow()` / `isSongInPlaylistSync()`: Checks if a song exists within a playlist (e.g. Liked Music check).

#### `SongStatsDao.kt` (`data/local/dao/SongStatsDao.kt`)

* **Bug / Health Check:** Uses `@Transaction` on `incrementPlayCount` to ensure atomic read-modify-write safety under concurrent coroutines. No issues found.

#### `AlarmDao.kt` (`data/local/dao/AlarmDao.kt`)
* **Purpose:** DAO for querying, inserting, updating, and removing system alarms.
* **Key Functions:**
  * `getAllAlarms()`, `getEnabledAlarms()`: Returns reactive flows or synchronous lists for reboot rescheduling.

#### `PendingDownloadDao.kt` (`data/local/dao/PendingDownloadDao.kt`)

* **Key Functions:** `insert()` (replace-on-conflict), `deleteByVideoId()`, `getAll()` (ordered by `queuedAt` ascending).

### 1.3 Database (`data/local/`)

#### `AppDatabase.kt` (`data/local/AppDatabase.kt`)
* **Purpose:** Central Room database class holding all entities (`Song`, `Playlist`, `PlaylistSongCrossRef`, `SongStats`, `Alarm`, `PendingDownload`) at **Version 8**.
* **Key Capabilities:**
  * Configured at Database Version 8. `MIGRATION_6_7` added the two YouTube-playlist-sync columns to `playlists`; `MIGRATION_7_8` added the `pending_downloads` table. Both are additive-only (`ALTER TABLE`/`CREATE TABLE IF NOT EXISTS`) and registered via `.addMigrations(...)` — deliberately never `fallbackToDestructiveMigration()` for a real version bump, since that would silently wipe every user's library, playlists, stats, and alarms.
  * Thread-safe double-checked locking singleton pattern via `@Volatile` and `synchronized(this)`.
* **Bug / Health Check:** Singleton creation is thread-safe and prevents multiple database instances. Schema version aligns with entities. No issues found.

### 1.4 Repositories (`data/repository/`)

#### `MusicRepository.kt` (`data/repository/MusicRepository.kt`)
* **Purpose:** Central source-of-truth repository coordinating access between local Room DAOs, `BackupManager`, smart playlists, and storage management.
* **Key Functions:**
  * `getRecentlyPlayedSongs()`, `getMostPlayedSongsWithStats()`: Combines `SongStatsDao` flows with `SongDao` lists into rich `SongWithStats` objects.
  * `ensureSmartPlaylistsExist()`: Automatically generates and deduplicates all six system playlists (`SMART_PLAYLIST_NAMES`: Liked Music, Top 50 Most Played, Recently Added, Unplayed, Downloads, Cloud Nine).
  * `getOrCreateLikedMusicPlaylistId()`, `toggleLikeSong()`, `isSongLiked()`: Manages the "Liked Music" system playlist logic.
  * `deletePlaylist()`: Blocks deletion of any smart playlist via `isProtectedSmartPlaylist()` — generalized from an earlier version that only checked "Liked Music" by name, which left Top 50/Recently Added/Unplayed actually deletable through the UI despite being meant to be permanent.
  * `playlistWithSongsFlow(playlist)` / `allPlaylistsWithSongs`: Single shared definition of "the songs in this playlist," correctly branching between a real cross-ref join and the matching computed query for each smart playlist. Used by `PlaylistViewModel`, `HomeViewModel`'s smart-playlist artwork lookup, and `StatsViewModel`'s storage breakdown, so this logic can't drift out of sync across screens.
  * `deduplicateLibrary()`: One-time cleanup merging duplicate `Song` rows (same `youtubeId`, or same normalized title+artist) — repoints playlist membership and merged play stats onto a surviving row (preferring a downloaded copy) and deletes the rest. Never touches files on disk. Gated by an `AppPreferences` flag so it only ever runs once.
  * `removeDownloadKeepInPlaylist(songId)`: Safely deletes the local audio file from disk while preserving track metadata and playlist associations as a streamable YouTube cloud track.
  * `buildRadioQueue(seedSong, limit=20)`: "Start Radio" queue builder -- same producer first, then same artist, then everything else, each tier weighted toward under-played tracks (grouped into play-count bands, least-played first, lightly shuffled within each band). No `genre` field exists in the schema, so this is producer/artist overlap only.
  * `likeSongs(songIds)` / `unlikeSongs(songIds)`: Bulk add/remove from Liked Music, used by `PlaylistDetailScreen`'s "Like all songs" / "Remove liked tag from all" overflow actions and its multi-select mode.
* **Bug / Health Check:** Comprehensive error handling for file deletion, duplicate smart playlist cleanup, and system playlist immutability protection. No issues found.

## 2. Utilities & Helper Packages (`utils/` / `data/local/`, `data/network/`, `ui/util/`)

#### `AiMetadataCleaner.kt` (`data/local/AiMetadataCleaner.kt`)
* **Purpose:** Fast pattern engine and optional AI metadata cleaning utility for music tracks.
* **Key Features:**
  1. **Offline Pattern Engine:** Extremely fast (< 1 ms), zero-memory regex engine stripping bracketed noise (`[Official Audio]`, `(Video)`), extracting producer credits (`prod.`, `produced by`), featured artists (`feat.`, `ft.`), and splitting `Artist - Title`.
  2. **Optional Online AI Engine:** If a Gemini or OpenAI API key is supplied in `AppPreferences`, sends a transient HTTP POST request on `Dispatchers.IO` with short timeouts (3s/5s).
* **Bug / Health Check:** `connection.disconnect()` is enclosed inside a mandatory `finally` block to guarantee HTTP connections are closed immediately, preventing memory leaks. Regexes are case-insensitive and robust. No issues found.

#### `LyricsRepository.kt` (`data/repository/LyricsRepository.kt`)
* **Purpose:** Multi-source lyrics engine for search, retrieval, parsing, and caching.
* **Key Capabilities:**
  * Queries LrcLib API (synced & plain lyrics), embedded ID3 tags via `MediaMetadataRetriever`, and YouTube/Piped captions (VTT and JSON formats).
  * `parseLyrics(rawLyrics)`: Helper function that parses LRC timestamp tags (`[mm:ss.xx]`) into structured `List<LyricLine>` sorted chronologically.
  * Caches non-blank lyrics in Room DB via `MusicRepository.updateSongLyrics`.
* **Bug / Health Check:** Releases `MediaMetadataRetriever` in `finally` blocks, closes OkHttp responses via `.use {}`, handles network/IO exceptions gracefully. No issues found.

#### `CoverArtScraper.kt` (`data/repository/CoverArtScraper.kt`)
* **Purpose:** High-resolution album cover scraper and local image cacher.
* **Key Capabilities:**
  * Queries iTunes Search API (converting `100x100` thumbnail URLs to `1000x1000` high-res image URLs), MusicBrainz / Cover Art Archive, and YouTube thumbnails, in that fallback order.
  * `matchesSong(candidateTitle, candidateArtist, song)`: normalizes and compares each search result's title/artist against the target `Song` before accepting its artwork. iTunes and MusicBrainz require a verified match (falling through to the next source, or to no artwork, rather than ever using an unverified result); YouTube's last-resort thumbnail tier still falls back to the top hit if nothing verifies.
  * Downloads image files to local storage (`Android/data/com.example.tgmusicai/files/Covers/{songId}.jpg`) and updates `artworkUri` in Room DB.
* **Bug / Health Check:** Fixed a real "wrong cover art" bug — all three sources previously took search result `[0]` unconditionally, and iTunes Search in particular does loose keyword matching (not artist+title pairing), so the first hit for "Artist Title" was often a same-titled track by a different artist, a cover, or a remix. `matchesSong` above is the fix. IO streams and file directories still properly managed; exception handling still prevents crashes on network failures.

#### `BackupManager.kt` (`data/local/BackupManager.kt`)
* **Purpose:** Handles portable `.tgmusic` zip backup export and restore operations.
* **Key Capabilities:**
  * **Export:** Serializes database entities (`Song`, `Playlist`, `PlaylistSongCrossRef`, `SongStats`, `Alarm`) into `manifest.json` and zips it along with local audio files into `Downloads/TGMusic_Backup_{timestamp}.tgmusic`.
  * **Import:** Reads `.tgmusic` zip package, validates paths against Zip Slip vulnerabilities (`canonicalPath` check), extracts audio files back to `Music/`, and restores Room DB tables without re-downloading.
* **Bug / Health Check:** Explicit Zip Slip path traversal security check included. Streams are buffered and safely closed. No issues found.

#### `NetworkObserver.kt` (`data/network/NetworkObserver.kt`)
* **Purpose:** Real-time internet connectivity observer utilizing Android's `ConnectivityManager`.
* **Key Features:**
  * Listens for `NET_CAPABILITY_INTERNET` network changes.
  * Exposes `isOnline: StateFlow<Boolean>` used across the UI to display offline state banners and filter downloaded tracks.
* **Bug / Health Check:** Gracefully catches registration exceptions and provides immediate initial network status check on startup. No issues found.

#### `SleepTimerManager.kt` (`playback/SleepTimerManager.kt`)
* **Purpose:** Countdown timer for auto-pausing playback after a user-selected time duration.
* **Key Features:**
  * Counts down in 1-second intervals on `Dispatchers.Main`.
  * Exposes `remainingMs: StateFlow<Long?>` for UI timer displays.
  * Executes `onTimerExpired` callback (pausing playback) when countdown reaches zero.
  * **Fade-out** lives in `PlayerViewModel`, not here: a collector on `remainingMs` ramps `MediaControllerManager.setVolume()` linearly to 0 over the last 30s (`SLEEP_FADE_WINDOW_MS`), restoring `1f` as soon as the timer expires or is cancelled.
* **Bug / Health Check:** Properly manages coroutine job lifecycle with `SupervisorJob()`. `cancelTimer()` cleanly stops active jobs without memory leaks. No issues found.

#### `AudioEffectsManager.kt` (`playback/AudioEffectsManager.kt`)
* **Purpose:** Thin wrapper around Android's system `Equalizer`/`BassBoost` audio effects for the 5-band equalizer + bass boost feature.
* **Key Features:**
  * `attach(sessionId)`: idempotent -- re-attaching to an already-attached session id is a no-op. Both effects operate on the platform mixer for a given audio session, so they can be owned by a UI-layer ViewModel instead of `PlaybackService` itself, as long as the session id matches (`MediaControllerManager.getAudioSessionId()`).
  * `setBandLevel`/`applyBandLevels`/`usePreset`/`setBassBoostStrength`/`currentBandLevels`/`presetNames`/`bandLevelRange`/`centerFreqHz`: direct passthroughs to the underlying `Equalizer`/`BassBoost`, each wrapped in a try/catch (`Log.e` + no-op) since these platform effects can throw if the session becomes invalid mid-call.
* **Bug / Health Check:** New in this session. All effect calls defensively caught; `release()` nulls both references.

#### `AppPreferences.kt` (`data/local/AppPreferences.kt`)
* **Purpose:** Preferences DataStore manager for persisting application settings.
* **Key Preference Keys:**
  * `ONBOARDING_COMPLETED`: Boolean flag tracking onboarding status.
  * `AI_API_KEY`: Saved Gemini or OpenAI API key for online AI metadata cleaning.
  * `SELECTED_THEME`: Saved color theme string (e.g. `"YT_DARK"`, `"PASTEL_MIDNIGHT"`, `"WARM_AMBER"`, `"NORDIC_SLATE"`).
  * `ALARM_FORCE_MAX_VOLUME` / `ALARM_VOLUME_RAMP_UP`: Booleans backing `AlarmsScreen`'s alarm-sound settings dialog, read by `AlarmPlaybackService` when an alarm fires.
  * `EQUALIZER_ENABLED` / `EQUALIZER_BAND_LEVELS` (comma-separated millibel string) / `EQUALIZER_PRESET_NAME` / `BASS_BOOST_STRENGTH`: Equalizer state, read/written by `EqualizerViewModel`.
* **Bug / Health Check:** Asynchronous, non-blocking DataStore implementation. Safe defaults provided for all preferences. No issues found.

#### `FormatUtils.kt` (`ui/util/FormatUtils.kt`)
* **Purpose:** Formatter utility object for time durations, date timestamps, and file name sanitization.
* **Key Functions:**
  * `formatDuration(durationMs)`: Converts milliseconds to `mm:ss` or `hh:mm:ss`.
  * `formatTimestamp(timestampMs)` / `formatTimeOfDay(timestampMs)`: Converts epoch time to readable date/time strings.
  * `sanitizeFileName(input)`: Strips illegal OS path characters (`\ / : * ? " < > |`), trims whitespace/dots, and bounds max file name length to 200 characters to prevent filesystem errors during downloads or exports.
* **Bug / Health Check:** Robust regex sanitization and locale-aware time formatting. No issues found.

## 3. Background Playback Layer (`playback/`)

#### `PlaybackService.kt` (`playback/PlaybackService.kt`)
* **Purpose:** Foreground/background media service extending `MediaLibraryService` for ExoPlayer audio playback with MediaSession and Android Auto browsing support.
* **Key Features:**
  * Exposes hierarchical media tree (`ROOT_ID` -> `CATEGORY_SONGS`, `CATEGORY_PLAYLISTS`, `CATEGORY_ARTISTS`) for head units and system media browsers.
  * Configured with `C.AUDIO_CONTENT_TYPE_MUSIC` and `C.USAGE_MEDIA` with automatic audio focus handling.
  * Recovers gracefully from playback errors by logging and automatically advancing to the next track.
  * **`maybeExtendQueueForAutoplay`:** Appends random downloaded songs directly to the live queue (`addMediaItems`) as soon as playback reaches the current last item (repeat off), so the queue never actually runs dry and the extension is visible/skippable in "Up Next" — not a reactive single-song swap after `STATE_ENDED` (that path, `playRandomSongAsAutoplay`, is now only a last-resort fallback).
  * **Notification tap-to-open:** `setSessionActivity` opens `MainActivity` to the Now Playing screen via `ACTION_OPEN_NOW_PLAYING`.
* **Bug / Health Check:** Clean Media3 session implementation. Coroutine scope cancelled on `onDestroy()`, ExoPlayer instance released properly. No issues found.

#### `MediaControllerManager.kt` (`playback/MediaControllerManager.kt`)
* **Purpose:** Application-scoped manager binding to `PlaybackService` via `MediaController`.
* **Key Features:**
  * Exposes reactive `StateFlow`s for active track (`currentSong`), playback state (`isPlaying`), position (`currentPositionMs`), track duration (`durationMs`), playback queue (`playlist`), shuffle mode, 3-state repeat mode (`repeatMode`), and `isResolving`.
  * Implements 3-State repeat loop cycle: `REPEAT_MODE_OFF` -> `REPEAT_MODE_ALL` -> `REPEAT_MODE_ONE` -> `REPEAT_MODE_OFF`.
  * **Progressive queue resolution:** resolves only the starting song before playback begins, then resolves the rest of a cloud queue concurrently in the background, patching each into the live queue via `Player.replaceMediaItem` as it finishes — replaced an earlier design that resolved the entire queue sequentially before playing anything, which on a multi-song cloud playlist could take as long as playing through the playlist would.
  * `moveQueueItem(from, to)`: reorders the live queue via `Player.moveMediaItem`; `onTimelineChanged` (`refreshQueueFromPlayer`) keeps the exposed `playlist` in sync with any timeline change, including ones made service-side (autoplay extension).
  * A fast path in `playSong` skips full queue re-marshaling when the target queue matches what's already loaded, just seeking instead — avoids re-sending potentially hundreds of `MediaItem`s over Binder IPC on every tap within the same list.
  * Runs a 500ms ticker job to emit continuous position updates and record real-listen-based play counts during active playback.
  * `setVolume(volume)`: passthrough to `controller?.volume`, used by the sleep timer fade-out.
  * `getAudioSessionId()`: passthrough to `controller?.audioSessionId`, used by `EqualizerViewModel` to attach `AudioEffectsManager`.
  * `setPlaybackSpeed(speed)` / `playbackSpeed: StateFlow<Float>`: sets `PlaybackParameters(speed, pitch=1f)` (0.5x-2.0x, pitch always preserved), exposed as a speed-preset menu in `NowPlayingScreen`.
* **Bug / Health Check:** Asynchronous future listener setup on main executor prevents UI thread locks. Position ticker cleanly cancelled on pause or release. No issues found.

#### `YouTubeSearchResult.kt` (`data/youtube/YouTubeSearchResult.kt`)
* **Purpose:** Data model representing a YouTube search result.
* **Fields:** `videoId`, `title`, `uploader`, `durationSeconds`, `thumbnailUri`.
* **Bug / Health Check:** Immutably typed data class. No issues found.

#### `YouTubeAudioStream.kt` (`data/youtube/YouTubeAudioStream.kt`)
* **Purpose:** Data model representing an extracted direct audio stream URL and format metadata.
* **Fields:** `url`, `format` (e.g. `"m4a"`, `"webm"`), `bitrate`.
* **Bug / Health Check:** Immutably typed data class. No issues found.

#### `YouTubeExtractor.kt` (`data/youtube/YouTubeExtractor.kt`)
* **Purpose:** YouTube extraction engine providing query search and direct audio stream extraction. Rebuilt from scratch (previous version's 6-tier chain of scraper sites and an unauthenticated InnerTube call was almost entirely non-functional).
* **Key Architecture & Mechanism:**
  * **Primary Extractor:** `NewPipeExtractor` (real library, not a scraper site) configured with a custom `NewPipeOkHttpDownloader` enforcing realistic Chrome browser User-Agent headers. Used directly for both search (`ServiceList.YouTube.getSearchExtractor`) and stream resolution (`StreamInfo.getInfo`, filtered to `DeliveryMethod.PROGRESSIVE_HTTP`, sorted by bitrate).
  * **Fallback:** If NewPipe fails, falls back to a curated Piped REST endpoint (`PIPED_ENDPOINTS`) then a curated Invidious REST endpoint cluster (`INVIDIOUS_ENDPOINTS`) — both verified-alive lists at time of writing, but public instances rotate/die and need periodic re-verification. Each candidate is pre-flight-checked with `verifyStreamUrl` (HTTP `Range` GET expecting 200/206). Both tiers also have a self-healing live instance directory fallback (`fetchLivePipedInstances`/`fetchLiveInvidiousInstances`), consulted lazily (only if the hardcoded hosts fail) with a short 4s timeout and cached once per process — an earlier eager, 15s-timeout version made a single dead hardcoded host stall every affected song by 15s, which on a multi-song "Play All" looked like the app had frozen.
  * **Known caveat:** NewPipe-direct stream resolution can be blocked by YouTube's IP-based bot detection on datacenter/cloud networks (confirmed from this project's dev sandbox — not video-specific, not a library-version bug). The Piped fallback exists specifically to route around this since Piped resolves server-side.
* **Bug / Health Check:** Verified end-to-end with a live network test during the rebuild (real search results, real stream URL, real HTTP 206 partial-content response through the Piped fallback). Network streams closed safely via `.use {}`.

#### `CloudDownloadManager.kt` (`data/youtube/CloudDownloadManager.kt`)
* **Purpose:** Background cloud audio downloader for downloading YouTube streams directly into local device storage with progress tracking, metadata cleaning, cover art scraping, and Room DB indexing.
* **Key Features & Pipeline:**
  * **Deduplication Check (`checkAndDeduplicate`):** Before initiating a stream download, queries Room DB by `youtube_id` or `title` + `artist` metadata to verify if the track is already stored locally. If a local file exists, reuses the local URI and skips re-downloading! The same widened existing-row lookup runs again when indexing a freshly completed download, updating an existing cloud-placeholder row in place instead of inserting a duplicate.
  * **Resumable queue:** Every enqueue writes a `PendingDownload` row (deleted on completion/failure); `resumePendingDownloads()` re-enqueues anything left over on next launch. `downloadPlaylist()` marks the whole batch "Queued" in `downloadMap` immediately rather than only as each song's turn comes up in the sequential download loop.
  * **Audio Stream Storage:** Saves downloaded M4A/WebM audio tracks into local device storage (`Android/data/com.example.tgmusicai/files/Music/` or `files/Music/`) with sanitized filenames (`FormatUtils.sanitizeFileName`).
  * **Progress Tracking:** Emits real-time state updates (`IDLE`, `EXTRACTING`, `DOWNLOADING`, `COMPLETED`, `FAILED`) and download fraction via `downloadMap: StateFlow<Map<String, DownloadProgressState>>`.
  * **Metadata Cleaning & Cover Art Scraping:** Cleans track titles and extracts artist/producer credits via `AiMetadataCleaner`, scrapes high-resolution cover art via `CoverArtScraper` (saved locally to `Android/data/com.example.tgmusicai/files/Covers/`), and indexes the complete track into Room DB via `SongDao`.
  * **Bulk Playlist Downloader:** Supports bulk downloading all undownloaded tracks in a cloud playlist.
* **Bug / Health Check:** Stream IO wrapped safely in `.use {}` blocks. Progress fraction clamped between `0f..1f`. File names sanitized with `FormatUtils.sanitizeFileName`. No issues found.

## 5. Alarm Subsystem (`alarm/`)

#### `AlarmScheduler.kt` (`alarm/AlarmScheduler.kt`)
* **Purpose:** Utility object for scheduling, canceling, and snoozing alarms via Android's `AlarmManager`.
* **Key Features:**
  * Uses `AlarmManager.setAlarmClock` on API 21+ for exact delivery even during Doze mode while showing the system clock icon.
  * `calculateNextTriggerTime`: Accurately calculates target timestamps for single or repeating day-of-week alarms (`repeatDays`).
  * Checks exact alarm permissions (`canScheduleExactAlarms` on API 31+) with fallback to `setAndAllowWhileIdle`.
* **Bug / Health Check:** Security exceptions on Android 12+ caught and handled gracefully with inexact alarm fallbacks. No issues found.

#### `AlarmReceiver.kt` (`alarm/AlarmReceiver.kt`)
* **Purpose:** System `BroadcastReceiver` invoked when a scheduled alarm trigger fires.
* **Key Features:**
  * Uses `goAsync()` to safely execute asynchronous Room DB queries off the main thread.
  * Starts `AlarmPlaybackService` directly (`AlarmPlaybackService.start(context, alarmId)`) -- does **not** build a notification or launch `AlarmActivity` itself; the service owns both.
  * Automatically updates non-repeating alarms to disabled or reschedules repeating alarms for their next occurrence.
* **Bug / Health Check:** `pendingResult.finish()` enclosed in a mandatory `finally` block to prevent BroadcastReceiver timeouts. No issues found.

#### `AlarmPlaybackService.kt` (`alarm/AlarmPlaybackService.kt`)
* **Purpose:** Foreground `Service` that owns all alarm audio and the alarm notification, started directly by `AlarmReceiver` the instant an alarm fires.
* **Key Features:**

* **Bug / Health Check:** Fixed a real "alarm sent a notification but made no sound" bug — a full-screen-intent notification only auto-launches its Activity when the device is locked or the screen is off; with the screen already on and unlocked, Android instead shows a plain heads-up notification and waits for a tap. Running playback from a service started directly by the receiver fixes this regardless of screen state. **Verified on a real device** (screen on, unlocked, app foregrounded — the exact failing case) after this fix: sound plays.

## 8. On-Device AI Containment Layer (`ai/`)

Added per an explicit request to bring on-device AI in "in a container in a non-invasive way ... so even if they break it doesn't brick the whole app." Two real, verified, open-weight models are bundled in `app/src/main/assets/ai/` (not placeholders -- both were downloaded and their file headers/tensor names were checked byte-for-byte):

- **`yamnet.tflite`** (Google YAMNet, Apache 2.0, ~4.1MB): classifies audio into 521 AudioSet classes. `yamnet_class_map.csv` (522 rows) maps indices to names; **indices 132-276** are music genres/instruments/moods, the curated range `SongTaggingEngine` filters to.
- **`minilm_quantized.onnx`** (`Xenova/all-MiniLM-L6-v2`, int8, Apache 2.0, ~23MB) + `vocab.txt` (30522-token BERT WordPiece vocab): turns lyrics text into a 384-dim sentence embedding for similarity/grouping. Verified by grepping the raw `.onnx` bytes that it exposes `input_ids`/`attention_mask`/`token_type_ids` inputs and a `last_hidden_state` output -- the standard HuggingFace Optimum export shape -- rather than assuming.

**Containment mechanics** (why a break here can't break the app):
1. Every engine (`SongTaggingEngine`, `LyricsEmbeddingEngine`) lazily initializes inside a try-catch; failure sets a permanent `initFailed` flag for that process instead of retrying, and every subsequent call short-circuits to `AiModelResult.Unavailable`.
2. Every inference call is *also* individually try-caught, so one bad file/input returns `AiModelResult.Error` for that call without disabling the engine for the next song.
3. `AiFeatureManager` -- the only class anything outside `ai/` should touch -- wraps everything a third time and runs on its own `SupervisorJob`-backed `CoroutineScope`, so a coroutine cancellation or crash inside it can't propagate to a caller's scope.
4. Results live in a brand-new, standalone `ai_song_tags` Room table (additive `MIGRATION_8_9`, see `AppDatabase.kt`) that nothing else in the app reads or joins against -- a corrupted row here is fully inert to the rest of the schema.
5. The only wiring into existing code is two nullable constructor parameters (`LibraryViewModel.aiFeatureManager`, `SongItem.onAnalyzeWithAiClicked`) that are `null` by default -- the app compiles and runs identically with the AI container entirely removed.

**Trigger point (deliberately singular for this pass):** `SongItem`'s overflow menu has an "Analyze (AI)" entry (Library screen only) wired to `LibraryViewModel.analyzeSongWithAi(song)`, which calls `AiFeatureManager.analyzeSong(song)` and shows the resulting tags via a Toast. `AiFeatureManager.rankBySimilarLyrics(seedId, candidateIds)` exists for a future "Start Radio by lyrical theme" upgrade but isn't wired into `MusicRepository.buildRadioQueue` yet -- that queue builder still uses producer/artist overlap only (see Subsystem 11 in `ARCHITECTURE_CHEAT_SHEET.md`).

**Build status:** `assembleDebug` succeeds with both native libraries (`libtensorflowlite_jni.so`, `libonnxruntime.so`) correctly packaged for every ABI. **Device-verified**: real on-device inference produces correct tags (e.g. "Music", genre/instrument tags) for real library songs. A debug build's APK size grew by roughly 100MB because Gradle bundles all four native ABIs unstripped for every third-party `.so`; a real release via Android App Bundle would only ship the one ABI a given device needs, closer to the ~27MB the two model assets themselves add.

**Post-verification fixes (device testing surfaced a real accuracy bug, not a model-quality problem):**
- `PcmDecoder` previously always decoded from the start of the file, which for most songs is a quiet/instrumental intro -- YAMNet frequently scored "Silence" as the top tag as a result. It now seeks to roughly 25% into any track long enough to have a real intro before decoding its analysis window, which fixed the "AI tagging is weak / doesn't recognize music" issue without needing a different model.
- `SongTaggingEngine.SCORE_THRESHOLD` was lowered from `0.15f` to `0.08f` based on real observed score magnitudes on-device (the "Music" label typically scores 0.3-0.4; real secondary genre/instrument tags typically score 0.08-0.15, and were being filtered out entirely at the old threshold).
- `MainActivity` now runs a one-time backfill (`AppPreferences.hasBackfilledAiTagsV1Flow` dedup flag, matching the pattern used for other one-time migrations) that tags every already-downloaded song exactly once, and `CloudDownloadManager` calls `AiFeatureManager.analyzeSongIfNeeded` after every new download completes so new songs get tagged automatically without a manual "Analyze (AI)" tap.
- `LibraryScreen`'s grid view previously had no overflow menu at all (`SongGridItem` had zero actions beyond tap-to-play), so switching to grid view silently lost "Add to Playlist", "Start Radio", "Fetch Cover Art & Lyrics", and "Analyze (AI)". `SongGridItem` now has the same overflow menu as the list view, and the Library selection-mode top bar has a bulk "more" menu (bulk scrape, bulk radio-from-first-selected, bulk AI analyze) so multi-select has full parity with single-item actions in both view modes.

## 9. Bug Fixes From Live Device Testing (2026-09-13 session)

A round of user-reported bugs found by actually using the freshly-installed build, each root-caused via live logcat instrumentation and/or direct testing of the external APIs involved rather than guessed at:

- **Cover art not updating everywhere (`ui/util/FormatUtils.kt`):** `CoverArtScraper` always overwrites the same fixed path (`Covers/{songId}.jpg`), so `Song.artworkUri` never changes string value on a re-scrape -- Coil's cache is keyed by that unchanged URI string, so some screens kept showing stale art while others (with different recomposition timing) showed the fresh file. Fixed with `FormatUtils.cacheBustedArtworkUri()`, which appends the artwork file's `lastModified()` timestamp as a `?lm=` query param so Coil treats an overwritten-in-place file as a new resource. Applied at every `AsyncImage` site that displays `Song.artworkUri` app-wide (Library list/grid, MiniPlayer, Now Playing, Queue, playlist screens, alarm song picker, Home, Stats) -- verified live on-device that a re-scraped song's new art now shows correctly in the Library list.
- **YouTube-captions lyrics tier was completely non-functional (`data/repository/LyricsRepository.kt`):** `fetchFromYouTubeCaptions` called a Piped endpoint (`/captions/{videoId}`) that does not exist on the real Piped API (confirmed via direct curl: unconditional raw-HTML 404 for every video) -- this tier had never worked. Fixed to use the actual documented endpoint (`/streams/{videoId}`'s `subtitles` array), and to rewrite the caption track URL's format from the default `fmt=ttml` (XML, unparseable by the existing code) to `fmt=vtt` (plain WebVTT, already handled). Verified live end-to-end: a song with no LrcLib/embedded-ID3 match successfully fetched, parsed, and persisted real YouTube caption text via this tier. Separately, `videoId` resolution now prefers `song.youtubeId` before falling back to parsing it out of `mediaUri` (which is a local `file://` path for any already-downloaded song and can never match the URL-pattern regex) or a fresh search.
- **Auto-generated captions on sung content are frequently just `[Music]`/`[Applause]` tags with no real words** (YouTube's auto-caption speech recognition generally can't transcribe singing). `LyricsRepository.hasRealSpeechContent()` now rejects a parsed caption result that's almost entirely non-speech tags, so this tier no longer caches unhelpful placeholder text as if it were real lyrics.
- **"Play All" on an all-cloud playlist could rapid-cycle through every song ("Cloud Nine" skip-storm) (`playback/PlaybackService.kt`):** `MediaControllerManager.playInternal` loads the whole queue's `MediaItem`s immediately (real stream URLs resolve asynchronously afterward via `resolveRemainingInBackground`), so if stream resolution fails for a run of songs in a row (dead/rate-limited Piped & Invidious mirrors, in the case observed live), ExoPlayer's `onPlayerError` used to unconditionally auto-skip to the next item every time, cascading through the entire queue in under a second. `PlaybackService` now tracks `consecutivePlaybackErrors` and only auto-skips while it's `<= MAX_CONSECUTIVE_PLAYBACK_ERRORS` (2); beyond that it pauses instead of continuing to skip, resetting to 0 on the next successful `onIsPlayingChanged(isPlaying = true)`. Verified live: the log line `"Stopping auto-skip after 3 consecutive playback error(s)"` fired and playback settled into a normal paused state instead of cycling through all 12 songs.
- **Stats Bug: direct-streamed (not downloaded) YouTube plays were never tracked (`ui/viewmodel/YouTubeViewModel.kt`):** `playTrack()` built a transient `Song(id = 0, ...)` and played it directly without ever inserting it into Room, so `song_stats` had nothing to attach a play to. Now calls `MusicRepository.ensurePersisted(streamSong)` (dedupes by `youtubeId`/`mediaUri`) before playback and plays the copy with the resulting real id.
- **Stats Bug: "Total Track Plays" undercounted any library with more than 10 played songs (`ui/screens/StatsScreen.kt`):** it was computed as `mostPlayed.sumOf { it.stats.playCount }`, where `mostPlayed` is capped at the top 10 songs. Replaced with a true whole-library aggregate: `SongStatsDao.getTotalPlayCount()` (`SELECT COALESCE(SUM(playCount), 0) FROM song_stats`), exposed through `MusicRepository`/`StatsViewModel` as `totalPlayCount`.
- **Stats screen redesign (initial pass):** added a "Top Artists" section with ranked progress bars and real album-art thumbnails on the "Most Played Songs" list. Superseded by the full redesign in Section 10 below, which the user asked for after this pass turned out incomplete.

## 10. Second Round of Fixes: Full Stats Redesign, Cloud Nine Resilience, Lyrics Correctness (2026-09-13, later same day)

The user reported the Section 9 Stats pass was incomplete relative to `STATS_TAB_ANALYSIS_AND_DESIGN.md`, that Cloud Nine was still broken, and that lyrics had a new "shows the literal word null" bug plus bad sync -- backed by two fresh Gemini analysis docs (`LYRICS_AND_AI_TAGGING_ANALYSIS.md`, `CLOUD_NINE_PLAYBACK_BUG_ANALYSIS.md`). This section covers the full follow-up pass.

### Stats: schema, background telemetry, and the rest of the redesign
- **Bug 1 (the real one): background/after-Activity-death listening was never tracked.** Play/listen-time tracking lived entirely in `MediaControllerManager`, whose `CoroutineScope` is cancelled by `MainActivity.onDestroy()` (`mediaControllerManager.release()`) -- meaning any song played after the Activity is destroyed (backgrounded and reclaimed, or simply closed) stopped being tracked at all, even though `PlaybackService` (a real foreground service) kept the music playing. Moved all of it into `PlaybackService` itself, which owns the actual `ExoPlayer` and runs independently of Activity lifecycle: `trackedSongId`/`trackedMediaId`/`trackedYoutubeId` state, a `startTelemetryTicker`/`stopTelemetryTicker` pair driven by `onIsPlayingChanged`, and `resetListenTracking` on `onMediaItemTransition`. Song identity is resolved from the real DB id embedded directly in the `MediaItem`'s extras (`SongMediaExtras.songId()`), falling back to a URI/YouTube-id DB lookup only if that's absent -- this also mostly neutralizes the doc's Bug 2 (URI-mismatch play-tracking) since the embedded id never depends on which URI variant (watch-page vs. resolved CDN) happens to be current. `MediaControllerManager` now only mirrors position/duration for the UI; its now-dead `repository`/`recordSongPlayedByMediaUri` plumbing was removed.
- **Schema (Bug 5): `AppDatabase` MIGRATION_9_10** adds `song_stats.totalListenTimeMs` and a new `listening_history` table (`songId`, `timestampMs`, `durationMs`) via `ListeningHistoryDao`. `PlaybackService` flushes accumulated listen time to both every ~10s of actual playback (`LISTEN_TIME_FLUSH_INTERVAL_MS`), and on pause/track-change/service-destroy so a shorter listen isn't lost.
- **Full Component A-F redesign implemented in `StatsScreen.kt`:** `WrappedHeroSummaryCard` (total listening time in h/m, total plays, rough daily average over the trailing week -- reads `StatsViewModel.totalListenTimeMs`/`totalPlayCount`), `WeeklyListeningBarChart` (Canvas bar chart over `MusicRepository.getWeeklyListeningTrend()`, which zero-fills all 7 days rather than omitting days with no listening), metallic gold/silver/bronze rank circles on the top 3 "Most Played Songs" rows, `TopArtistsDonutCard` (Canvas donut + legend, replacing the earlier plain progress-bar list), a new "Top Producers" horizontally-scrolling row (`MusicRepository.getTopProducers`, aggregated from `Song.producer` -- populated by `AiMetadataCleaner`), and a segmented multi-color storage bar on the Storage tab's hero card showing the top playlists' real share of total bytes (not the doc's decorative fixed 70/20/10 split).
- Colors for both the artist donut and the storage segments come from a small shared `chartColorFor(index, scheme)` palette cycling through the app's own Material 3 scheme colors, not hardcoded hex values, so the chart matches whatever theme is active.

### Cloud Nine: reducing how often the cascade guard even needs to fire
The cascade guard added in Section 9 already stops a skip-storm after a few failures, but `CLOUD_NINE_PLAYBACK_BUG_ANALYSIS.md` (and live testing) pointed at a further problem: `playQueueProgressively`'s background resolution fired one concurrent network request per remaining queue song the instant "Play All" was tapped -- a burst of ~11 simultaneous requests at the single shared Piped mirror for an all-cloud playlist, which live testing showed getting answered with a wall of 401/403s (self-inflicted rate-limiting, not a real outage).
- **`YouTubeExtractor`**: added an in-memory `streamCache` (keyed by videoId, TTL derived from the CDN URL's own `expire=` param when present, else a 4h default) so replaying/re-encountering the same video doesn't re-resolve it; added a separate 5s-timeout `preflightClient` for `verifyStreamUrl`'s pre-flight liveness check (previously shared the real request client's 15s timeout, so one dead candidate could stall resolution for 15s before falling through).
- **`MediaControllerManager`**: `resolveRemainingInBackground` now runs its concurrent resolutions through a `Semaphore(2)`, capping how many stream-resolution requests hit the mirror(s) at once instead of firing the whole queue simultaneously; a new `resolveAheadIfNeeded()`, called on every `onMediaItemTransition`, eagerly re-resolves the *next* queue item if it's still an unresolved watch URL by the time playback reaches the current one -- a just-in-time safety net independent of how far the bulk background resolution has gotten. **Verified live**: a repeat "Play All" on Cloud Nine during a window of genuinely-down mirrors (500/401/403 responses across Piped and Invidious) used only 2 concurrent resolution threads (confirmed via logcat thread IDs) instead of the previous ~11-way simultaneous burst, and the cascade guard still stopped cleanly after 3 failures.

### Lyrics: the actual root causes per `LYRICS_AND_AI_TAGGING_ANALYSIS.md`
- **The literal word "null" appearing as lyrics -- root cause found and fixed.** `org.json`'s `JSONObject.optString(key, fallback)` only returns `fallback` when `key` is *missing*; when `key` is present with an explicit JSON `null` value, it returns the 4-character string `"null"` (the stringified `JSONObject.NULL` sentinel) instead. LrcLib's API returns exactly this shape -- `"syncedLyrics": null` when a track only has plain lyrics, or vice versa -- so `fetchFromLrcLib` was caching the literal text `"null"` as if it were real lyrics whenever only one of the two fields was populated, and it passed the `isNotBlank()` check because "null" isn't blank. Fixed via a `JSONObject.stringOrEmpty(key)` helper (`if (isNull(key)) "" else optString(key, "")`) applied everywhere this file parses external JSON (LrcLib's `syncedLyrics`/`plainLyrics`, the Piped captions track `code`/`url` fields, and the JSON-transcript caption format's `text` field). **Verified live**: found 12 songs in the library DB with lyrics literally equal to the string `"null"`; force-refetching one ("Deathly Loneliness Attacks") after the fix produced its real lyrics text instead.
- **Bad LRC sync ("lyrics run seconds ahead") -- root cause found and fixed.** The old `LRC_PATTERN` only matched dot-separated centiseconds (`[mm:ss.ff]`); any line using colon-separated centiseconds (`[mm:ss:ff]`, common from some LRC generators) or any other unparseable line (including plain metadata tags like `[ar: Artist]`) fell back to `timestampMs = 0L`. Since the whole line list was then sorted by timestamp whenever *any* real timestamped line existed, every one of those `0L` lines sorted to the very front of the list -- ahead of the real first lyric -- corrupting the index-to-timestamp mapping for the rest of the song and making the highlighted "active" line correspond to text from a different point in the song than where playback actually was. Replaced with a `Regex`-based parser that matches both centisecond separators, handles multiple timestamp tags on one line (a legitimate LRC repeated-chorus construct), explicitly drops metadata tags, and gives any genuinely unparseable line a distinct `-1` sentinel that's excluded from the sort entirely (rather than colliding with a real `0ms` first line).
- **WebVTT cue-tag stripping**: `parseVttOrJsonCaptions`'s WebVTT branch now strips inline `<...>` formatting/speaker/per-word-timestamp tags (`<c.colorFFFFFF>`, `<v Speaker>`, `<i>`, per-word `<00:12.345>`) before appending caption text, instead of passing them straight through into what's shown as lyrics.
- **Streamed (unpersisted) songs' fetched lyrics never survived a replay**: `PlayerViewModel.fetchLyrics`/`scrapeArtworkAndLyrics` now call `MusicRepository.ensurePersisted` first for any `id == 0L` song (a direct YouTube stream never added to a playlist or downloaded) before fetching/saving, so `updateSongLyrics` has a real row to land on instead of silently affecting zero rows.
- **Auto-scroll fighting manual scroll**: `NowPlayingScreen`'s lyrics auto-scroll (`LaunchedEffect(activeIndex) { listState.animateScrollToItem(...) }`) now checks `!listState.isScrollInProgress` first, so dragging through the lyrics to read ahead no longer gets yanked back to the currently-playing line on every position tick. Also fixed two related `timestampMs > 0` comparisons (the active-line lookup and the tap-to-seek handler) to `>= 0`, since a real synced line can legitimately start at exactly 0ms and the new parser's `-1` sentinel (not `0`) is what actually marks "no timestamp" now.
- **Known non-bug, confirmed via raw data inspection**: a user report of lyrics lines appearing 2-3 times in a row (e.g. "Deconversion // 【SynthV Original】") was traced to the raw scraped WebVTT caption data itself containing the same text across 2-3 consecutive cues at near-identical timestamps -- YouTube auto-captions' own "rolling reveal" style, not a parsing bug. Left as-is per the user's explicit instruction.
