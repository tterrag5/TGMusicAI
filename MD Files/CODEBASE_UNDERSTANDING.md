# TGMusicAI — Codebase Understanding (Auditor's Own Assessment)

This document is written from scratch after two full line-by-line audit passes over every production and test file in the app (except the YouTube subsystem, which is being rebuilt separately — see the note at the end). It is not a copy of the older `PROJECT_EXPLANATION.md` / `ARCHITECTURE_CHEAT_SHEET.md` docs, which were written by a much weaker model and contained real inaccuracies (wrong package name in several places, a stale description of the YouTube tier structure, self-contradicting theme names, stale test counts). Treat this file as the current, verified account.

## 1. What the app actually is

TGMusicAI is a single-Activity Jetpack Compose Android app (`com.example.tgmusicai`, minSdk 24, targetSdk 37) that plays local on-device audio and (intended to) cloud-streamed YouTube audio through one unified library. Everything hangs off a single Room database (`AppDatabase`, version 7 as of the Google-sync work in §5, with a real `Migration(6, 7)` for the two new `playlists` columns — still `fallbackToDestructiveMigration()` for anything before v6) with five tables: `songs`, `playlists`, `playlist_song_cross_ref`, `song_stats`, `alarms`.

**Data flow, top to bottom:**
- `MainActivity` is the composition root. It builds one `AppDatabase`, one `MusicRepository`, one `NetworkObserver`, one `LyricsRepository`, one `CoverArtScraper`, and one `MediaControllerManager` directly in `onCreate()`, then hands them to a set of `ViewModel`s constructed via manual `ViewModelProvider.Factory` classes (no DI framework — Hilt/Koin are not used anywhere). Every screen gets its dependencies threaded down as constructor/composable parameters.
- `MusicRepository` is the single source of truth. It doesn't talk to Android APIs directly — it wraps four Room DAOs (`SongDao`, `PlaylistDao`, `SongStatsDao`, `AlarmDao`) plus a `BackupManager`. It also owns the "smart playlist" concept: four rows in the `playlists` table (`Liked Music`, `Top 50 Most Played`, `Recently Added`, `Unplayed`) are auto-created by `ensureSmartPlaylistsExist()` and flagged `isSmart = true`. Only `Liked Music` is backed by real `playlist_song_cross_ref` rows (populated by `toggleLikeSong`); the other three are *computed on the fly* from `SongStatsDao`/`SongDao` queries every time they're viewed and are never actually linked via cross-refs. This distinction matters a lot for correctness (see §2).
- Playback is Media3 ExoPlayer wrapped twice: `PlaybackService` (a `MediaLibraryService` that owns the real `ExoPlayer` instance, runs in the background, and exposes a browsable tree for Android Auto) and `MediaControllerManager` (an app-process-side client that binds to the service via `MediaController` and republishes ExoPlayer's state as `StateFlow`s for Compose to collect). `MediaControllerManager` is instantiated fresh in `MainActivity.onCreate()` — it is **not** an Application-scoped or ViewModel-scoped singleton, so every Activity recreation (e.g. a screen rotation) tears down and rebuilds the entire controller connection. This works but is wasteful and architecturally the weakest link in the playback stack (see §2).
- The alarm subsystem (`alarm/`) is a self-contained clone of a standard Android alarm-clock feature: `AlarmScheduler` wraps `AlarmManager.setAlarmClock`/`setExactAndAllowWhileIdle` with a `SecurityException` fallback to inexact scheduling; `AlarmReceiver` and `BootReceiver` are `goAsync()`-based `BroadcastReceiver`s; `AlarmActivity` is a `setShowWhenLocked` full-screen `ComponentActivity` running its own private `ExoPlayer` (deliberately `handleAudioFocus = false`, since an alarm must not be silently ducked by another app holding focus) with a `Player.Listener` that falls back to the system ringtone on any playback error.
- `LyricsRepository` and `CoverArtScraper` are both "try several real APIs in order, return the first real hit" scrapers (LrcLib → embedded ID3 → YouTube captions for lyrics; iTunes Search → MusicBrainz/CoverArtArchive → YouTube thumbnail for art). Both are genuinely functional against real, still-alive public APIs (iTunes Search and MusicBrainz in particular are stable, well-documented, unauthenticated APIs — these are the most trustworthy network code in the app).
- UI is 100% Jetpack Compose, Navigation 3 (`NavDisplay` + a `mutableStateListOf<NavKey>` backstack, not the older Navigation-Compose library), with a `ModalNavigationDrawer` for the sidebar and a `NavigationBar` for the five main tabs (Home, Explore/YouTube, Library, Playlists, Alarms, Stats).

## 2. Least-thought-out / most fragile parts (be specific, not diplomatic)

This section is deliberately blunt, per the audit's instructions.

### a) [FIXED during the YouTube rebuild] Playing a "cloud" (non-downloaded) song from anywhere except the YouTube tab was broken
`MediaControllerManager.buildMediaItem(song)` did `Uri.parse(song.mediaUri)` unconditionally. For a song with `isDownloaded = false`, `mediaUri` could be a plain `https://www.youtube.com/watch?v=...` page URL — not a directly-playable audio stream — with zero re-extraction anywhere in the play path. Fixed by adding `MediaControllerManager.resolveQueueForPlayback()`, called from both `playSong()` and `playQueue()`: any song whose `mediaUri` matches the unresolved-watch-URL pattern and has a `youtubeId` is re-resolved through a lazily-created `YouTubeExtractor` before being handed to ExoPlayer. Best-effort (a song that fails to resolve is left as-is and surfaces a normal ExoPlayer error rather than being silently dropped).

### b) `MediaControllerManager` is Activity-scoped, not process-scoped
Constructed fresh in `MainActivity.onCreate()`, released in `onDestroy()`. Every configuration change (rotation, some multi-window transitions) tears down the `MediaController` binding and reconnects from scratch. It works because `PlaybackService` itself survives independently, but the UI-side state (`StateFlow`s) and the 500ms position ticker restart every single time, which is wasted work and a plausible source of a visible playback-control "hiccup" on rotation that would be easy to miss in manual testing (most testers don't rotate their phone mid-song). This should really be hoisted to `Application` scope or a top-level ViewModel that survives configuration changes.

### c) The three computed "smart" playlists silently do nothing when you try to edit them
`Top 50 Most Played`, `Recently Added`, and `Unplayed` are not real playlists in the relational sense — they're query results dressed up as `Playlist` rows. Before this pass, `PlaylistDetailScreen` showed a working-looking "remove from playlist" button on every song in every playlist, including these three computed ones; tapping it deleted a `playlist_song_cross_ref` row that was never created, so nothing happened and the song reappeared on the next recomposition, with no error or explanation. (Fixed this pass by hiding the button for the three computed playlists — see the fix list.) This is a good example of the class of bug this app has a lot of: something *looks* wired up and interactive but the underlying data model doesn't actually support the action.

### d) No dependency injection, and dependencies are wired by hand in three or four places
`MainActivity`, `MainScreen`, and several `Factory` classes each manually thread the same five or six objects (`repository`, `lyricsRepository`, `coverArtScraper`, `mediaControllerManager`, `networkObserver`) down through constructor parameters. It works at the current size of the app, but it means every new feature that needs one of these objects requires editing multiple files to pass it through, and there's no compile-time guarantee two `ViewModel`s aren't accidentally holding two different repository instances (they aren't, currently, but nothing prevents it as the app grows).

### e) `AppDatabase` uses `fallbackToDestructiveMigration()` with no versioned migrations at all
Every schema change so far has been handled by bumping the version int and letting Room wipe and recreate the database. This is fine for a personal project still under heavy development, but it means **any future schema change will silently delete every user's local library, playlists, stats, and alarms** with no warning. There is no migration path back out of this once the app has real users. This is worth deciding on deliberately rather than continuing to bump the version number as a reflex.

### f) The YouTube-adjacent fallback lists were duplicated per-file before this pass
`LyricsRepository`'s caption fetcher hardcoded a single Piped mirror (`pipedapi.kavin.rocks`) while `YouTubeExtractor` maintains a six-entry rotating `PIPED_ENDPOINTS` list specifically because individual public Piped instances die or rate-limit constantly. Fixed this pass to share the same list, but it's a sign that cross-cutting "which public mirror do we trust today" concerns aren't centralized — anyone adding a new feature that touches Piped/Invidious needs to remember to reuse `YouTubeExtractor`'s constants rather than hardcoding a URL, and nothing enforces that.

### g) The "Liked Music" protected-playlist check was implemented three different, subtly wrong ways before this pass
`MusicRepository.deletePlaylist()` correctly required both `isSmart == true` AND an exact-case name match. But `PlaylistCard`, `PinnedPlaylistCard`, `SmartPlaylistCard`, and `PlaylistDetailScreen` each independently re-implemented "is this the Liked Music playlist" as a case-insensitive name-only check, with no shared helper. The practical consequence: a user who names their own custom playlist "liked music" (any case) would have had their delete button silently hidden in the UI even though the repository would have honored the deletion — a permanent-looking dead end for a perfectly ordinary playlist. Fixed this pass everywhere it was found, but the underlying issue — no single shared `Playlist.isProtectedSystemPlaylist()`-style helper — remains; it would be easy for a future screen to reintroduce the same mistake.

### h) Test coverage exists but several tests validate hand-copied logic, not the real function
`AuditAndSeekingTest.testDurationDivisionByZeroGuards` and `ConvenienceFeaturesTest.testDeduplicationMatchingLogic` re-type the guard/matching expression inline in the test rather than calling a shared, testable function — because the real logic lives inlined inside a `@Composable` (the slider math in `MiniPlayer`/`NowPlayingScreen`) or inside the out-of-scope `CloudDownloadManager.checkAndDeduplicate`. These tests will keep passing even if the real inline code drifts from the copied expression. Not touched this pass since it's a testability/refactor question, not a bug, but worth knowing the "100% green test suite" doesn't mean every claimed behavior is actually exercised end-to-end.

## 3. What's solid

For balance: the Room layer (entities/DAOs/transactions), the alarm subsystem's exception handling, `AiMetadataCleaner`'s regex engine, `BackupManager`'s Zip Slip protection (after this pass's boundary fix), and the cover-art/lyrics scrapers against iTunes/MusicBrainz/LrcLib are all genuinely well-built and defensively coded. The bugs found in this app cluster almost entirely around (1) UI/data-model mismatches for the computed smart playlists, (2) the YouTube-dependent playback path, and (3) copy-pasted logic that drifted between files — not around basic Room/Compose/coroutine hygiene, which is consistently good.

## 4. YouTube subsystem — rebuilt, live-verified, and now the least-thought-out part's replacement

`YouTubeExtractor.kt` was rewritten from a ~1390-line, 6-tier chain (Cobalt API, YT1s API, a raw web-embed HTML scrape, and an unauthenticated raw InnerTube POST, alongside Piped/Invidious) down to ~440 lines: NewPipeExtractor as the primary path for both search and stream resolution (`StreamInfo.getInfo`, filtered to `DeliveryMethod.PROGRESSIVE_HTTP`, sorted by bitrate), with a curated Piped/Invidious fallback. Every deleted tier was either a scraper site never meant for this kind of access, or missing the auth YouTube's real API requires — none of them were ever likely to work reliably.

**Live-verified end-to-end, twice** — once via a JVM test hitting real network calls, and once on an actual physical Android device (search → real results with real thumbnails → tap play → real Piped-resolved stream → confirmed audio playback with a advancing position and 171s of real buffered audio in the system media session → download button → real 1.3MB `.m4a` file saved to disk with matching content-length, plus scraped cover art).

**Direct NewPipe→YouTube stream resolution was found to be non-functional and was removed entirely** (kept only for search, which works great). It hit `ContentNotAvailableException: The page needs to be reloaded` on every video tried, across two library versions (v0.24.6, v0.24.8) and — critically — two completely independent real networks (a cloud dev sandbox AND a physical Android device on its own network/carrier). That combination rules out "sandbox IP is flagged" as the sole explanation; this looks like a broad, current YouTube anti-bot measure (the WEB client player endpoint now wants a PoToken NewPipeExtractor can't produce without a JS-challenge solver) that a real user's device could plausibly hit too. Stream extraction now goes directly to Piped (tier 1, verified working end-to-end) then Invidious (tier 2, augmented with a live-fetched instance list from `api.invidious.io/instances.json` so it self-heals as instances rotate — Piped has no equivalent working public directory as of this writing).

This means **the Piped/Invidious endpoint lists are not a nice-to-have fallback — they're load-bearing**, and need periodic re-verification since public instances rotate/die fast (only 1 of ~20 candidate Piped instances checked during this work were actually fully functional; most Invidious instances returned 401/403). Re-check with `curl -o /dev/null -w '%{http_code}' https://<host>/streams/<videoId>` if search/playback ever silently stops working again — that's the most likely cause.

**Separately, a real UI bug was found and fixed during this same testing session**: `MainScreen.kt`'s navigation drawer had every color hardcoded to YT_DARK's literal values (`Color(0xFF030303)`, `Color.White`, etc.) instead of `MaterialTheme.colorScheme.*` tokens, so the drawer never matched any theme other than YT_DARK. Fixed and visually confirmed on-device by switching to Warm Amber and reopening the drawer.

## 5. Google account YouTube playlist sync (new feature, added after the YouTube rebuild)

Requested by the user: link a Google account, list every playlist on it (not just Liked Videos), let the user pick which to import, and keep imported ones up to date automatically. Deliberately built on the regular YouTube Data API (`youtube.readonly` scope) rather than any YT Music unofficial API, since YT Music playlists already show up in regular YouTube.

- **`data/google/GoogleAuthManager.kt`** — wraps `Identity.getAuthorizationClient(activity)` (Google Play Services Identity/Authorization API). This is a backend-less, "Android-type" OAuth client tied to the app's package name + release/debug signing cert SHA-1 (registered in Google Cloud Console — client ID `152586353165-ltb8h4mv7rnn9acgku1hb65jfoiuu5ng.apps.googleusercontent.com`). `getAccessToken()` first tries silent authorization; if `hasResolution()` comes back (first-time consent needed), it launches the system consent bottom sheet via an `ActivityResultLauncher` that **must be registered in `MainActivity.onCreate()` before the Activity reaches `STARTED`** — this is why `GoogleAuthManager`/`YouTubeDataApiClient`/`YouTubePlaylistSyncManager` are constructed before `setContent {}` rather than inside a `remember` in Compose.
- **`data/google/YouTubeDataApiClient.kt`** — thin REST wrapper around `playlists.list`, `playlistItems.list`, `videos.list`, `channels.list`. The Liked Videos playlist has the fixed, special ID `"LL"` and is always offered first in the import UI, separate from the user's real created playlists.
- **`data/google/YouTubePlaylistSyncManager.kt`** — `importPlaylist`/`importLikedVideos` create a local `Playlist` row tagged with `youtubePlaylistId`; `syncAll`/`syncPlaylistById` do a **diff-based** re-sync (add new cross-refs, remove stale ones) rather than delete-and-recreate, so a synced playlist's `Song` rows are never orphaned or re-downloaded unnecessarily.
- **`ui/viewmodel/GoogleSyncViewModel.refreshAllSynced()`** has a deliberate guard: `if (playlistDao.getYoutubeSyncedPlaylistsList().isEmpty()) return@launch` before ever calling `authManager.getAccessToken()`. Without this, every app startup (via the `LaunchedEffect(Unit) { googleSyncViewModel.refreshAllSynced() }` in `MainActivity`) would silently try to sign the user into Google, which would be surprising for anyone who has never touched the feature. Get this guard right if this code is ever touched again.
- **Schema change**: `Playlist` gained `youtubePlaylistId: String?` and `lastSyncedAt: Long?`, shipped as `AppDatabase` version 6→7 with a real `Migration(6, 7)` (two additive `ALTER TABLE` statements) — deliberately not `fallbackToDestructiveMigration()`, since that would wipe every real user's library on upgrade.
- **UI entry point**: a new "Import from YouTube" item in `MainScreen`'s navigation drawer opens `GoogleSyncScreen` (sign-in prompt → list of the account's playlists with Liked Videos pinned first → tap to import → "Synced Playlists" section with per-playlist last-synced time and a manual refresh action).
- **Gotcha hit during this build**: adding 5 new `PlaylistDao` interface methods (`getPlaylistByYoutubeId`, `getYoutubeSyncedPlaylists`, `getYoutubeSyncedPlaylistsList`, `updateLastSyncedAt`, `getSongIdsInPlaylist`) broke compilation of the unit test source set, because both `MusicRepositoryTest.kt`'s `FakePlaylistDao` and `ThemesAndLikedMusicTest.kt`'s `FakeTestPlaylistDao` are hand-written in-memory fakes implementing the full `PlaylistDao` interface directly (no mocking framework) — any interface change requires updating both fakes in lockstep. Fixed; all 50 unit tests plus `assembleDebug` pass as of this write-up.
- **Not yet live-verified on-device**: the OAuth consent flow, playlist listing, import, and sync all compile and unit-test-pass but have not been exercised on the physical device yet (the user pulled the test phone back for other use before this could happen). This is the top item to check the next time the device is available.

## 6. Other live-device bug reports fixed this session (pending device re-verification)

- **Liking a song didn't actually add it to the "Liked Music" playlist** for songs that hadn't been persisted to Room yet (e.g. a cloud/YouTube search result the user had never played or downloaded) — `toggleLikeSong(songId)` was being called with `songId = 0L` for such songs, a no-op against real rows. Fixed by adding `MusicRepository.ensurePersisted(song)` (inserts the song first, or reuses an existing row matched by `youtubeId`/`mediaUri` if one already exists) and calling it from `PlayerViewModel.toggleLikeCurrentSong()` before `toggleLikeSong`.
- **Rotating the phone changed which speaker/output the audio was using** — root cause was that `MediaControllerManager` is Activity-scoped (see §2b) and every rotation was tearing down and rebuilding the whole `MediaController`/`ExoPlayer` connection, which can cause Android to re-pick an audio route. Fixed by adding `android:configChanges="orientation|screenSize|screenLayout|keyboardHidden|uiMode"` to `MainActivity` in `AndroidManifest.xml`, so rotation no longer recreates the Activity (or `MediaControllerManager`) at all. This is a narrower fix than properly hoisting `MediaControllerManager` to process scope (§2b still stands as a real architectural weak point) but directly addresses the reported symptom.
